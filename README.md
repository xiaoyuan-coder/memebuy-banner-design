# Memebuy Banner Skill 团队使用说明

适用版本：V1.2.0｜更新日期：2026-10-28

这个 Skill 用于制作 Memebuy App 首页静态活动 Banner。提供业务需求、画风参考和必要素材后，AI 会整理文案、设计构图、生成图片并标注检查结果。团队主要参与三个环节：确认业务信息、选择画面方向、检查上线效果。

默认交付为 **1440×1000px、不透明 PNG**。首轮图片用于比较方向；选定后继续修改，完成内容与真实首页检查，才能进入上线交付。

## 1 首次使用

从维护者获取完整的 `memebuy-banner-design` 文件夹，保留 `SKILL.md`、`references/`、`scripts/` 和 `agents/`。其中包含规范、参考分析方法和检查工具，安装时一起保留。

可以将文件夹交给 Codex，并发送：

```text
请把我提供的 memebuy-banner-design 文件夹安装为本地 Skill。
安装后检查 SKILL.md 中的版本，确认是 V1.2.0，
并确认能读取制作规范和 scripts/check_banner.py。
```

代码保存在 [GitHub 仓库](https://github.com/xiaoyuan-coder/memebuy-banner-design)。从仓库获取时也请核对版本；版本较旧时，向维护者获取当前文件包。

使用时在对话里明确写上 `$memebuy-banner-design`，或从 Skill 选择器选中“Memebuy 首页 Banner”。如果没有找到，请先让 Codex 检查安装与识别状态；必要时重启后再试。安装与显式调用方式可参考 [OpenAI 官方 Skills 文档](https://learn.chatgpt.com/docs/build-skills)。

制作环境需要能读取附件、调用图像生成工具。完整执行本地图片检查还需要 Python 和 Pillow，这部分可以交给 Codex 检查和处理。

## 2 发起制作前准备什么

最关键的输入是：**这张图希望用户理解什么、点击后去哪里、希望借鉴哪种画风。**

| 提供内容 | 怎么说明 |
| --- | --- |
| 业务目标 | 介绍什么活动或功能，希望用户采取什么行动。 |
| 文案与业务事实 | 指定标题、按钮；说明哪些文字必须原样保留，哪些可以改写。涉及优惠时写清对象、门槛、日期等条件。 |
| 点击去向 | 例如选图页、活动详情页、商品页；暂未确定时明确标记待确认。 |
| 画风参考 | 上传参考图，说明喜欢它的字形、材质、角色画法或整体氛围。多张图请标明对应关系。 |
| 业务素材 | 要使用的角色、商品照片、Logo、印花等；注明必须保留的识别点。 |
| 数量与偏好 | 要几张、希望保留或避开什么颜色、有哪些明确不喜欢的表达。 |

请分清附件用途。例如：“图1只参考毛绒材质和字形；图2是必须使用的品牌角色；图3只参考构图。”这样能减少角色串用、商品外观变化和参考迁移偏差。

商品印花需要提供确认图案；允许使用探索示意时请明确说明。价格、优惠、日期和真实商品细节由业务方确认，AI 会针对关键缺口提问。

**可直接复制的首次需求：**

```text
使用 $memebuy-banner-design 制作 Memebuy 首页静态 Banner。

业务目标：让用户知道可以上传喜欢的图案，制作贴纸。
主标题：喜欢的图，印成贴纸。允许调整换行，文字保留。
按钮：选图打印。
点击去向：选图页。
辅助说明：本次无需额外说明。

参考图：附件1只参考毛绒材质、厚字和明快的配色关系，
主体换成与贴纸业务相关的原创形象。
商品素材：暂无，允许使用原创贴纸示意，交付时注明。
方向数量：3张，以常规构图为主，保留1张轻度探索。
颜色偏好：偏暖色，主题色从现有色表选择。

按当前1440×1000规范制作，每个方向首轮各生成一次。
交付时附上手机宽度预览、检查结果和待确认项。
```

以上是填写示例，实际文案、素材和偏好按本次业务替换。也可以先提供真实业务描述，让 AI 拟文案；必须逐字保留的内容请单独指出。

## 3 制作过程怎样配合

**第一步，整理需求并生成首轮。** AI 会检查业务信息、提炼参考特征、安排文案与主体，再生成完整 Banner。未指定数量时默认3个方向，通常2个常规、1个探索。常规方向可以共用左右构图，通过主体、字形、动作和材质形成差异。

**第二步，看图选方向。** 每个方向首轮各生成一次，并附上具体问题。此时重点判断活动是否清楚、画风是否接近预期、哪个方向值得继续。发现错字或越界时会如实标注，AI 会停在本轮等待选择。

**第三步，给出具体修改。** 选定图号，说明“保留什么、修改什么、还要检查什么”。建议一次集中给出本轮反馈，减少不同修改之间的冲突。

```text
选第2张继续，只修改这一张。

保留：右侧人物的粗线条、简化五官和紧凑动作，
保留现在的暖色关系与黏土材质。
修改：标题按“喜欢的图／印成贴纸”分两行，
收窄完整标题外框，按钮保留“选图打印”；删去左上角小角色。
检查：标题描边和投影、人物面部、按钮完整落入对应安全范围。

从原始参考和业务素材重新生成一版，
对照上一版检查保留项，标出仍未通过的内容。
```

“更高级一点”“感觉不对”也可以作为起点，最好再指出一个具体对象，例如颜色太杂、标题太小、角色不像参考、商品不够明显。如果暂时说不清，可以先让 AI 对照参考定位差异，再决定改动。

修订会把已认可的画法写成保留条件，从原始需求、参考和业务素材重新生成。旧成图用于比较，整图重新生成后仍需核对已认可部分是否发生变化。

## 4 当前规范需要记住什么

团队伙伴无需在每次需求中重复填写坐标，Skill 已包含这些规则。评审时重点留意以下内容：

| 项目 | 当前要求 |
| --- | --- |
| App 尺寸 | 1440×1000px，不透明 PNG，背景铺满四边。 |
| 顶部避让 | y=0–256，延续背景，重要文字、面部和商品关键细节避开这一区域。 |
| 核心内容 | x=70–1370、y=256–800，安排主要文字、活动按钮与主体关键部位。 |
| 标题范围 | 左右标题从y=301开始；居中及偏下布局另有范围，按所选布局检查。 |
| 底部避让 | y=806–1000，以背景和非关键装饰为主；新增y=960–1000仅承接背景与阴影。 |
| 手机阅读 | 在375px宽、约260.42px高的完整等比显示下检查标题、按钮和必要说明。 |
| 主题色 | 每张预先绑定现有C1–C12中的一个编号与HEX，画面与首页入口呼应。 |

安全区内要包含文字的描边、投影和毛绒等材质外沿。画面上下仍应自然延续背景，避免出现两条生硬的空白带。旧1440×960图片增加底部40px后，也需要按新顶部和标题范围重新检查。

每张 Banner 自身保留活动按钮；首页的双主入口、轮播指示条、状态栏和页面遮罩由页面显示，导出的素材保持纯画面。

完整坐标与主题色见[制作规范](references/production-rules.md)，原始说明与配图见[规范 PDF](references/source/Banner%20规范-v1.4.pdf)。

## 5 收到图片后怎么验收

先看手机宽度预览，快速确认：第一眼能读到标题，主体能解释活动，按钮清楚，必要条件读得清。再核对原图中的文字、角色、商品细节和边界。

交付时请让 AI 同时提供：

- App PNG，以及手机宽度预览和独立安全区检查图。
- 实际文案、标题布局、主题色编号与HEX。
- 具体未达标项，以及示意印花、商品外观等待确认项。
- 文件技术、内容边界、真实首页三项检查状态。

```text
请整理当前选定方向的交付文件，并逐项说明：
1. 文件是否为1440×1000、不透明PNG；
2. 标题完整外框、按钮、面部和商品关键细节是否通过边界检查；
3. 手机宽度下文字是否清楚；
4. 哪些素材或业务信息仍待确认；
5. 是否已经接入V2.2真实首页验收。
未检查的项目请标明待验收。
```

本地检查工具能检查尺寸、透明度，以及人工标注的内容外框；文字正确性、标注是否完整、画风和商品真实性仍需人工核对。文件尺寸通过后，还需要完成内容与页面检查。

上线前将素材放入V2.2真实首页，检查展开、滚动、吸顶和回到顶部时的效果，确认遮罩、双入口和指示条叠加后仍清楚，底部背景衔接自然，页面已取消额外10px延伸。缺少真实页面环境时，保留“真实首页待验收”状态。

## 6 常见情况怎么处理

| 遇到的情况 | 下一步 |
| --- | --- |
| 画风不够像参考 | 指出需要保留的造型、材质或空间关系，请AI对照主体、标题和背景分别定位差异。 |
| 内容太多、画面太乱 | 优先删除重复权益、可选说明和无作用道具，保留一个主张与清楚的主体关系。 |
| 标题过宽或越界 | 调整断行、字形宽度或布局，并重新测量描边和投影；保留手机阅读所需的视觉重量。 |
| 想加更多方向 | 明确追加数量、对应参考及希望探索的差异，再开始下一轮。 |
| 需要Web图片 | 明确提出Web交付；由App主稿固定裁切为1440×720，并另查裁切后的完整性。 |
| 需要动态Banner | 单独提出动态制作需求，明确素材与输出范围，按对应流程处理。 |
| 新开对话继续制作 | 重新提供原始参考、业务素材、选中稿和本轮反馈，写清保留项与改动项。 |

遇到反复出现的问题，请保留原始参考、需求、当轮提示词、成图和具体反馈，交给维护者复盘。后续迭代会依据这些记录更新方法，已确认的业务素材和当前产品规范继续作为制作基线。
